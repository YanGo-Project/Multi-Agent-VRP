# Multi-Agent VRP Solver

## Описание

Решатель **многоагентной задачи маршрутизации с динамической (зависящей от времени) ценой перехода**.
Несколько исполнителей (агентов) стартуют из своих депо, делят между собой общий пул клиентских точек
и совместно **максимизируют суммарный скор** посещённых точек; каждый маршрут при этом должен
укладываться в индивидуальные ограничения по времени, расстоянию и числу точек.

Это многоагентное обобщение одноагентного решателя [**TDTSP-PD**](https://github.com/YanGo-Project/TDTSP-PD).
Отличия от одноагентной версии:

- **N агентов** — у каждого своё стартовое/конечное депо (`depots` / `depots_end`), своя загрузка
  (`min_load` / `max_load`) и свои лимиты (`max_time` / `max_distance`).
- **Общий пул клиентов** — каждая точка может быть посещена не более чем одним агентом; набор
  непосещённых точек (`unvisited_points`) разделяется между агентами.
- **Inter-route операции** — перенос/обмен/склейка фрагментов маршрута **между разными агентами**.
- **Адаптивный выбор операторов** — рулеточный выбор операции по весам, обновляемым по успеху/неудаче.
- **Параллельная локальная оптимизация** агентов в отдельных потоках (по потоку на агента).

Цена перехода между точками зависит от времени: между 30-минутными срезами `time_matrix` она
вычисляется **линейной интерполяцией** (`TInputData::get_time_dependent_cost`).

## Формат данных

Входные и выходные данные имеют формат `*.json`. Структуры описаны в `utils/problem_arguments.hpp`,
парсинг и сериализация — в `utils/json_parser.cpp`.

### Входные данные (`TInputData`)

| Поле | Тип | Обяз. | Описание |
|------|-----|:----:|----------|
| `points_count` | `uint16` | да | Количество точек в задаче, включая депо |
| `agents_count` | `uint16` | да | Количество агентов (исполнителей) |
| `min_load` | `uint16[A]` | да | Минимальная загрузка (мин. число точек) на агента |
| `max_load` | `uint16[A]` | да | Максимальная загрузка (макс. число точек) на агента |
| `max_time` | `int64[A]` | да | Максимальное допустимое время маршрута на агента |
| `max_distance` | `int64[A]` | да | Максимальное допустимое расстояние маршрута на агента |
| `distance_matrix` | `int64[N][N]` | да | Статическая матрица расстояний между точками |
| `time_matrix` | `int64[T][N][N]` | да | `T` временных срезов матрицы времени; шаг между срезами — **30 минут** (`time_duration = 30*60`) |
| `point_scores` | `int64[]` | да | Массив «важностей» (ценностей) точек |
| `point_service_times` | `int64[]` | да | Массив времён обслуживания точек |
| `start_time` | `int64[A]` | нет | Время старта каждого агента (по умолчанию `0`) |
| `depots` | `uint16[A]` | нет | Стартовое депо каждого агента (по умолчанию `0`) |
| `depots_end` | `uint16[A]` | нет | Конечное депо каждого агента (по умолчанию — равно `depots`) |

> `A` = `agents_count`, `N` = `points_count`, `T` = число временных срезов.
> `distance_matrix` — статическая 2D-матрица; от времени зависит только `time_matrix`.

### Выходные данные

`main` пишет **два** JSON-файла с распределением точек по агентам — *до* и *после* локальной
оптимизации (`JsonParser::WriteAgentsJson`). Имена формируются из пути входного файла
(`MakeJsonPath`): для `problem.json` это `problem_before.json` и `problem_after.json`.

```jsonc
{
  "agents": [
    { "index": 0, "vertexes": [start_depo, v1, v2, ..., end_depo] },
    { "index": 1, "vertexes": [start_depo, ...,            end_depo] }
  ]
}
```

## Установка зависимостей

Используется библиотека [nlohmann/json](https://github.com/nlohmann/json).

**Linux:**
```bash
sudo apt install nlohmann-json3-dev
```
**macOS:**
```bash
brew install nlohmann-json
```

Зависимости Python-скриптов анализа — в `utils/requirements.txt`
(`pandas`, `matplotlib`, `numpy`): `pip install -r utils/requirements.txt`.

---

## Сборка проекта

```bash
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release .. && cmake --build .
```

После успешной сборки в папке `build/` появится исполняемый файл **`app`**
(собираются `utils/` + `src/` в статическую библиотеку `utils` и линкуются в `app`).

Опции сборки:
- по умолчанию компиляция идёт с `-O3`;
- `-DCMAKE_BUILD_TYPE=Debug` — включает `-DDEBUG`: в консоль выводятся промежуточные стадии и
  выполняется валидация метрик маршрута (`check_path_values`);
- `-DSAVE_STEPS=ON` — включает `-DSAVE_STEPS` (периодическое сохранение промежуточных решений).

---

## Аргументы программы

```bash
./app -p <problem.json> -t <seconds> [-i <iters>]
```

Аргументы, **реально влияющие** на работу `main`:

| Флаг | Дефолт | Описание |
|:----:|:------:|----------|
| `-p` | — | Путь до входного `.json` с задачей |
| `-t` | `0` | **Лимит времени** локальной оптимизации, в секундах (`0` — без лимита) |
| `-i` | `15` | `max_iter_without_solution` — задаёт число итераций главного цикла без улучшения (критерий останова) |

Пример:
```bash
./build/app -p datasets/many/top/Set_100_234/problem.json -t 10
```
В консоль выводятся скоры агентов до и после оптимизации и статистика адаптивных весов операторов;
рядом с входным файлом появляются `problem_before.json` и `problem_after.json`.

## Алгоритм

Работа делится на две части.

### 1. Первый шаг — построение начальных маршрутов

Реализация: `src/first_step.cpp`, `include/first_step.hpp`.

Для **каждого агента по очереди** запускается **динамическое программирование по битовой маске
посещённых вершин** (`DoFirstStep<true>` — версия с динамической ценой перехода). В каждом состоянии
DP хранится до **`TOP_SOLUTIONS_COUNT = 7`** лучших кандидатов.

### 2. Второй шаг — локальная оптимизация (`Optimize`)

Реализация: `src/algorithm.cpp` + операции в `src/inner_operation.cpp` и `src/inter_operation.cpp`.

Главный цикл выполняет на каждой итерации **фиксированную последовательность** из двух фаз:

1. **Inner (внутри маршрута)** — для **всех агентов параллельно**, по `std::thread` на агента
   (`DoInnerOptimization`). Конкретная операция выбирается **адаптивно** (рулетка по весам,
   `TOperatorSelector::SelectInnerOp`). Операции (`include/inner_operation.hpp`):
   `SwapAdjacent`, `SwapAny`, `Shift`, `TwoOpt`, `OrOpt`, `PickUnvisited`, `Drop`, `Replace`,
   `DoubleBridge`. Три из них (`PickUnvisited`, `Drop`, `Replace`) меняют **общий** пул
   `unvisited_points`/`visited_points`, поэтому защищены глобальным `try_lock`-мьютексом
   (при неудаче захвата итерация пропускается).
2. **Inter (между маршрутами)** — если агентов > 1, для **одной случайной пары** путей
   (`DoInterOptimization`). Операция выбирается адаптивно (`SelectInterOp`). Операции
   (`include/inter_operation.hpp`): `Relocate`, `Swap`, `TwoOpt`, `Cross`, `RelocateSegment`,
   `Glue` (склейка двух маршрутов в один, внутренняя оптимизация склейки до
   `max_glue_inner_optimization_iterations` итераций, затем поиск лучшей точки разреза обратно на два).

Адаптивные веса трёхуровневые (`include/adaptive_weights.hpp`, `operator_selector.hpp`): отдельные
веса inner-операций на каждый путь, общие веса inter-операций и уровневые веса. После каждой итерации
успех/неудача обеих фаз фиксируется через `UpdateLevel(Inner/Inter, …)` и `UpdateInner/InterOp(…)`;
сам **порядок выполнения фаз фиксирован** (`SelectLevel` для выбора фазы в цикле не вызывается).

Критерий останова — `inter_iterations_without_improve` итераций без улучшения
**или** лимит времени `-t`. По завершении печатается статистика весов и success-rate операторов.
